# 复现报告：Steering LLMs between Code Execution and Textual Reasoning (ICLR'25)

> 对象论文：*Steering LLMs between Code Execution and Textual Reasoning*（arXiv 2410.03524，ICLR'25）
> 复现子集：15 个任务 × 5 个方法 × 3 种思考模式，主模型 DeepSeek（`deepseek-flash`），2026-11-19 完成。

---

## 1. 一句话结论

**论文的核心结论方向被复现出来了**：在 15 个任务上，`Code+Text+Sum.`（代码 + 文本 + 汇总器）在三种思考模式下**平均分都是第一名**（AveNorm 99.4 / 99.4 / 99.7），而"让模型多写代码"本身并不能稳定提升成绩（`All Code+CoT` 在 A 组只有 77.2，远低于纯文本的 88.8）。

但有三处必须打折：①本轮最高分已接近上限（多数任务 96~100%），**方法间差异被天花板效应压缩**，而且在少数任务上 Sum 并不是第一（如 A 组的 Letters(sentence)：OnlyQ 88 > Sum 80）；②B 组有 2 个任务的 0% 是输出预算被思考耗尽造成的假象（已单独做敏感性重跑：预算提到 8000 后回到 12~40%，见第 6 节）；③BoxNet / Path Plan / BoxLift 三个规划任务在 2500 预算下普遍只有 0~25%，是预算与模型能力共同限制，不能用来区分方法优劣。

## 2. 实验设置

| 项目 | 设置 |
|---|---|
| 仓库 | `CodeSteer-v1.0`（原地不动，所有补丁在 `repro/` 里 monkey-patch） |
| 主模型 | DeepSeek `deepseek-flash`（思考模式下有 `reasoning_content`） |
| 裁判模型 | 同为 `deepseek-flash`，但**永远关闭思考**（否则三组之间的分数变化分不清是主模型还是裁判变了） |
| 任务 | 论文 Table 2 的 14 个任务 + 自加的第 15 个任务「英文字句字母计数」 |
| 方法 | 5 个：`1_only_ques`(OnlyQ)、`All_text`、`All_code_CoT`、`AutoGen`、`Text_code_summarizer`(Code+Text+Sum.) |
| 砍掉的方法 | `Code Interpreter` 系列（国产模型无 CI 通道）、`AutoGen System`（runner 未接 system message 分支）、`Self-estimate Score`（仓库未实现） |
| 样本量 | 每任务 25 个（A 组原始跑到 50，统计时统一按前 25 个算；navigate 因 A 组只出 11 个，三组统一按 11 个比） |
| 代码执行 | 子进程，超时 30s（论文 30s） |
| 思考模式 | A = `off`（不带思考）；B = `strip`（开思考但**丢弃** `reasoning_content`，只把 `content` 往下游传）；C = `on`（把 `reasoning_content + content` 一起往下游传） |
| 思考预算 | 2500 tokens（敏感性实验用 8000） |
| 归一化 | `AveNorm_j = (1/N) Σ_i s_ij / max_i(s_i)`（论文口径，但 max 只在我这 5 个方法里取，论文是 10 个方法，所以绝对值不可直接比，**名次和方向可比**） |

规模：合计 **24,865 次 API 调用**，输入 16.2M tokens、输出 10.5M tokens；按 DeepSeek 官方价目表（`deepseek-flash`：输入 1~2 元/百万，输出 4~8 元/百万，空闲时段半价）折算约 **58~116 元**人民币。其中正式三组 23,648 次调用（约 44~87 元），敏感性重跑 1,217 次调用（约 15~29 元）。

> 上面只是**产出结论的那部分**。把两次返工（修 `-c` 路径 bug 之前的一夜、思考预算误设 8000 的一夜）和冒烟测试都算上，整轮复现共调用 **56,084 次、输入 34.34M / 输出 20.61M tokens，约 117~234 元**（缓存命中口径下 83~166 元）。完整账单与省钱建议见**第 10 节**。

三点观察：

1. **"只给问题"（OnlyQ）时模型会自发写代码**：Blocksworld 15%、Path Plan 14%。这正对应论文说的"模型对代码通道的偏好/过度自信"——没人让它写，它自己写。

**关键差异（必须说明）**：

1. **分数天花板**。论文里 GPT-4o 的 AveNorm 是 80 上下，本次多数任务 96~100%，方法差异被压缩到几个点以内。原因是 2026 年的 `deepseek-flash` 已在 MATH/GSM/BBH 上很强，任务本身对它是"送分题"。真正能区分方法的只剩 Game 24、MATH-Geometry、Path Plan、BoxLift、Letters(sentence)、Blocksworld 这几个。
2. **绝对分数不可比**。归一化的 max 只在我这 5 个方法里取（论文是 10 个方法），加上模型不同，**只能比名次和方向**，不能比绝对值。
3. **论文的"inverse scaling / 过度自信用代码"只能部分对照**。本次用一个近似口径统计了代码使用率（见 3.5），方向与论文一致：不给指令时模型也会自发写代码（OnlyQ 在 Blocksworld 15%、Path Plan 14%），且"写了代码"不等于"代码有用"。论文 Table 3 的精确口径（按 turn 统计）没有严格复刻。

## 5. 三个思考模式的解读（本次自加的维度）

**B 组 ≠ A 组 + 一个滤镜。** 开思考后模型会把推导写进 `reasoning_content`，正文退化成很短的碎片（B 组正文中位数只有 16 个字符，42% 的调用正文 < 20 字符）。这些碎片常常**就是答案**（如 `<<<12/25/1937>>>`），所以短答案任务（BBH 系列）B 组不掉分；但需要正文带代码块/推导的任务（MATH-Geometry、Letters(sentence)、Path Plan）B 组会掉，因为 runner 的判分链路是"从正文抽代码块 → 执行 → 读 stdout → 裁判抠答案"，信息一少就抽错。

**B vs C 的差距（丢思考 vs 留思考）**：OnlyQ 94.8 vs 94.3、AllText 89.7 vs 91.4、AllCode+CoT 89.1 vs 90.5、AutoGen 92.7 vs 93.2、Sum 99.4 vs 99.7 —— **平均只差 0.7 个点**。也就是说，对这套"再多轮 refine + 汇总"的流水线，**思考内容下游用不用得上，影响很小**；真正起作用的是"开不开思考"（A→B 五个方法平均 +4.6 点）。

顺带一个好玩的读数：OnlyQ 上 B（94.8）比 C（94.3）还高。因为"只给问题"这种单轮设定里，把思考文本拼回正文反而给裁判塞了更多噪声（裁判要从长文本里抠答案）。

**A→B 的增益**主要来自：AllCode+CoT +11.9、AutoGen +5.6、OnlyQ +4.5。A 组里 code 类方法最差，恰恰是因为关思考时模型写的代码"能跑但思路错"（Blocksworld 只打印 `Move B from 1 to 2` 没包 `<<<>>>`，导致 JSON 抽取全空）。

## 6. 已知偏差（不修正就不能下结论的部分）

### 6.1 B 组 path_plan / BoxNet 的 0% —— 预算截断，非方法效应

`repro/truncation_audit.py` 扫描结果：

| 模式 | 样本 | 正文为空 |
|---|---|---|
| off | 1350 | 0 (0.0%) |
| strip | 1350 | **377 (27.9%)** |
| on | 1350 | 0 (0.0%) |

空正文 100% 集中在 strip 组的 `boxnet1`（5 方法 × 25 = 125）与 `path_plan`（5 方法 × 25 = 125），且这些调用的 `completion_tokens` **恰好等于 2500 预算**。定点探测（`repro/probe_truncation.py`，同一 prompt 分别给 2500 / 8000 / 16000）：

- 2500 → `out_chars = 0`（全被思考吃光）
- 8000 → `out_chars = 7`
- 16000 → `out_chars = 19~240`（答案出来了）

**结论：B 组这两个任务的 0% 是"预算不够"的产物，不能读成"丢弃思考有害"。** 敏感性重跑（8000 预算）结果见 6.2。

### 6.2 敏感性重跑（strip × path_plan/BoxNet1 × 8000 预算）

同一批样本，只把思考预算从 2500 提到 8000，重跑（结果在 `results/sens_strip_b8k/`）：

| 任务 | 方法 | 预算 2500 | n | 预算 8000 | n |
|---|---|---|---|---|---|
| Path Plan | OnlyQ | 0.0 | 25 | **32.0** | 25 |
| Path Plan | AllText | 0.0 | 25 | **20.0** | 25 |
| Path Plan | AllCode+CoT | 0.0 | 25 | **20.0** | 25 |
| Path Plan | AutoGen | 0.0 | 25 | **32.0** | 25 |
| Path Plan | Code+Text+Sum | 0.0 | 25 | **40.0** | 25 |
| BoxNet | OnlyQ | 0.0 | 25 | **16.0** | 25 |
| BoxNet | AllText | 0.0 | 25 | **12.0** | 25 |
| BoxNet | AllCode+CoT | 0.0 | 25 | **20.0** | 25 |
| BoxNet | AutoGen | 0.0 | 25 | **16.0** | 25 |
| BoxNet | Code+Text+Sum | 0.0 | 25 | 50.0 | 10（未跑完） |

**结论：B 组这两个任务的 0% 完全是预算产物。** 只要把预算从 2500 提到 8000，同样的样本、同样的模型，分数就从 0 变成 12~40%。而且恢复之后**方法的排序也恢复了**：Path Plan 上 Sum 40 > OnlyQ/AutoGen 32 > AllText/AllCode 20，与 A 组、C 组"Sum 最好"的方向一致 —— 这说明 B 组那两个 0% 不是"丢弃思考"的效应，只是预算把小任务的分数一起打没了。

⚠ 两点保留：

1. **但 8000 也不够**：B 组在 8000 下的 Path Plan（20~40%）仍明显低于 A 组（36~64%）和 C 组（52~72%）。也就是说预算解释了"0%"，但**解释不了"低"**——开思考 + 丢弃思考内容，在长规划任务上确实比关思考差。这是 B 组唯一真实存在的劣势，其余任务上 B 与 C 基本持平。
2. `BoxNet × Code+Text+Sum` 的 8000 数据只跑了 10/25 就按时间停掉（每样本 70~90 秒）。其余 9 个格子都是 25/25 满样本。

作为对照，C 组（留思考）在 8000 下的零散数据也显示同方向：Path Plan OnlyQ 60 → 96、AllText 68 → 100（n=25/7），说明**只要 thinking token 够，这个模型在这两个任务上的真实水平远高于 2500 预算下的读数**。所以 3.2/3.3 表里这三个任务（Path Plan、BoxNet、BoxLift）只能横向比方法，不能当"模型在该任务上的绝对能力"。

### 6.3 Blocksworld 上 AllCode+CoT 12%（A 组）—— 格式对不上，非代码执行失败

`benchmark/run_Blocksworld_baseline_methods.py:201-232` 会把 `response` 换成代码的 `result.stdout` 再去抽答案。模型写的代码是 `print("Move B from 1 to 2")`，**没包 `<<<>>>`**，于是 `extracted_answer_1.txt` 恒为 `<<<No answer found>>>`，而 `extracted_answer_2`（正文里的代码块）也不是答案 → 两个都对不上。手动跑同一份 `code_1_0.py`：`rc=0, stdout='Move B from 1 to 2'`，执行本身没问题。GPT-4o 当年会包 `<<<>>>`，这一代模型不会。

### 6.4 三个规划任务的低分是真实能力不足

BoxNet（0~16%）、Path Plan（A 组 36~64%，C 组 52~72%）、BoxLift（0~25%）三组都很低，与判分无关：这些任务要求多步空间规划，`deepseek-flash` 做不了。它们只能说明"方法之间差异"（Path Plan 上 Sum 64/72 明显更好），不能说明"整体难度"。

## 7. 复现过程中踩到并修掉的坑（供他人参考）

1. **`python3` 在 Windows 上不存在** → `env_win.py` 把所有 `["python3", ...]` 命令改写成当前解释器。
2. **`python -c "exec(open('C:\...').read())"` 的 `\U` 被当 unicode 转义** → 子进程 `SyntaxError`，stdout 永远为空，**整批实验的代码执行全程空转**（曾导致"代码方法看起来更差"的假结论）。修法：把该参数里的 `\` 全换成 `/`。
3. **模型白名单**：runner 里 `if model_name in [...]:` 走 API、否则走本地 HF 权重加载。国产模型名必须进白名单，否则报 `NameError: run_response`。
4. **判分器硬编码 `gpt-4o`**：`GPT_response(..., model_name='gpt-4o')` 的调用点要单独路由到裁判模型，且裁判始终关思考。
5. **样本计数写死 `total_sample_num += 1`**：所有 runner 都有这一行，是统一注入样本上限的好锚点；但 `big_bench_hard` 一个 runner 跑 4 个子任务，计数必须按子任务拆，否则第一个子任务把配额吃光。
6. **思考预算**：给 8000 时单次调用 70s、正文为空；2500 是这批任务的合理值（仍然是 B 组截断的根源，见 6.1）。
7. **`<<<...>>>` 抽取要用最后一个匹配**：开思考后正文里会掺中间猜测，取第一个会判错（曾把 C 组 letters 判成 12%）。
8. **字母计数任务的"位置"定义必须写进题面**：删空格后编号、标点也占位，否则真值和模型的合理理解差 4 个位置。

## 12. 分数是怎么算的、可信到什么程度

### 12.1 三层口径

**第一层：单个样本对错**（写进 `success_failure.txt`，只有 `True` / `False` 两种取值，已核验）。不同任务走三条不同的判分路径：

| 路径 | 适用任务 | 判定方式 |
|---|---|---|
| 双 LLM 裁判 | gsm、MATH-Geometry、MATH-C&P、number_multiply、BIG-Bench-Hard、Blocksworld、Path Plan | 先从「代码输出」和「原始正文」各抽一个答案（LLM 抽取），再分别让裁判比较一次（`is_equiv_func`，允许 1e-3 相对误差、忽略单位/格式），**两个都判 False 才算错** |
| 状态模拟 | BoxNet、BoxLift | 解析模型给的动作序列，跑状态机，检查箱子最终是否到达目标 |
| 本地精确比较 | Letters（单词）、Letters(sentence)（自加任务）、Game 24（表达式求值） | 纯代码比对，不调 LLM |

**第二层：任务准确率** = 该任务被计入的样本中 `True` 的比例（本次每任务 25 个，navigate 11 个）。

**第三层：AveNorm** = 先对每个任务，用「该任务上 5 个方法里的最高分」做分母归一到 0~1，再对 15 个任务取算术平均。论文是 10 个方法里取 max，所以**绝对值不可比，名次和方向可比**。

### 12.2 三个可能高估的漏洞，逐个查过

| 漏洞 | 后果 | 实测 |
|---|---|---|
| 原仓库判定是 `if r1=='False' and r2=='False': 错 else: 对`，只要裁判回复里没有 `<<<True>>>/<<<False>>>`（被截断、跑偏、回空），就会**静默算作答对** | 系统性高估 | 走 LLM 裁判的 4,990 个样本里，裁判两个候选都解析不出的 **0 个（0.0%）** —— 这条漏洞没被触发（`repro/score_audit.py`） |
| 判对的样本是不是真凭「True」判的 | 可能靠 else 分支白捡 | 判对样本里 **96.3% / 96.3% / 98.3%**（A/B/C 组）两个候选都判 True；靠「只要一个对」的口径只多 2~4%；**两个抽取答案都为空/`No answer found` 却判对：0 个** |
| LLM 裁判自己会不会比错 | 误判 | 见下表的本地交叉验证 |

### 12.3 与「本地精确比较」交叉验证（MATH 两个任务，1,000 个样本）

用 sympy 从数据集标准答案（`\boxed{}`）重建真值，本地判等（多项式化简 + 1e-3 相对误差），与 LLM 裁判逐样本对照（`repro/judge_validate.py`，零 API 成本）：

| 组 | 样本 | 裁判判对 | 本地确认对（精确率） | 本地算对中裁判也判对（召回率） | 一致率 |
|---|---|---|---|---|---|
| A off | 500 | 479 | **479（100.0%）** | 479/481（99.6%） | 99.6% |
| B strip | 250 | 225 | 224（99.6%） | 224/224（100%） | 99.6% |
| C on | 250 | 241 | 240（99.6%） | 240/240（100%） | 99.6% |

**结论：LLM 裁判在 MATH 这类有确定数值答案的任务上几乎不出错。** 需要说明的是，我第一版本地比较器只做到 86% 一致率，逐条看下来 **23 个"误判"全部是我的解析器错**（`\frac{640}{3}\pi`、`108\sqrt{3}-36`、`1,\!000,\!000`、`\frac1{216}` 这类），裁判都是对的 —— 这本身是个教训：自写对答案脚本很容易自信地错，反而是 LLM 裁判更稳。

### 12.4 哪些分数不能信

1. **Blocksworld 的 `All Code+CoT` 12% 是低估**（6.3 节）：模型答对了，但代码输出没包 `<<<>>>`，抽取器抓空。
2. **strip 组的 Path Plan / BoxNet 0% 是低估**（6.1/6.2 节）：思考 token 把输出预算吃光，正文为空。这是预算问题，不是判分问题。
3. **天花板效应**：多数任务 96~100%，方法之间差 1~4 个点。**每任务 25 个样本，单个任务准确率的标准误约 ±4~8 个百分点**（n=25、p≈0.9 时 95% 置信区间约 ±12 点），所以单个任务上的小差异不要当真；对 15 个任务取平均后误差约降到 ±2~3 点，AveNorm 上的 2 点以上差距才比较可靠。
4. **裁判与主模型同源**（都是 `deepseek-flash`），存在同族偏好的风险；本次在 MATH 上没有观察到系统性偏差，但换模型做迁移验证时应重新审计。
5. **AveNorm 只在 5 个方法内归一**，所以 99.4 这个数不代表"模型水平"，只代表"在这 5 个方法里的相对位置"。

**一句话**：单个样本的对错判定是可信的（0% 解析失败、MATH 上与精确解 99.6% 一致）；**方法之间 1~3 个点的差距不可信**，5 个点以上、且方向跨任务一致（如 Code+Text+Sum. 在 15 个任务里三组都第一）才可信。

## 13. 为什么分数这么高？逐个因素拆开

总分落在 77~99（AveNorm），远高于论文的 67~79。这不是单一原因，是四个因素叠加，加一条无法排除的风险。

### 13.1 因素一：模型代差（真实的能力提升，占大头）

论文测的是 2024 年的 GPT-4o / GPT-4o-mini / GPT-3.5 / O1-preview / Claude-3-Sonnet / Mixtral-8x7b；本次是 2026 年的 `deepseek-flash`。同一类任务上的原始准确率变化非常剧烈：

| 任务 | 论文 GPT-4o（Only Question） | 本次 deepseek-flash（A 组 OnlyQ） |
|---|---|---|
| Number Multiplying | 37% | **96%** |
| GSM-Hard | ~50% | 92% |
| Date Understanding | ~84% | 96% |
| Web of Lies | ~91% | 100% |

多位数乘法从 37% 到 96%，是两代模型的差距，不是判分问题。

### 13.2 因素二：任务饱和（高分主要是题目变简单了）

15 个任务里，有 **6 个（C 组 8 个）**是"5 个方法全部 ≥95%"的饱和任务：

| 组 | 饱和任务 | 数量 |
|---|---|---|
| A off | MATH-C&P 98.4、Date U. 96.8、Logical Ded. 100、Web of Lies 100、Letters 100、Number Mult. 98.4 | 6/15 |
| B strip | Logical Ded. 99.2、Navigate 100、Web of Lies 99.2、Blocksworld 98.4、Letters 100、Number Mult. 100 | 6/15 |
| C on | MATH-C&P、Logical Ded.、Navigate、Web of Lies、Blocksworld、Game 24、Letters、Number Mult. 全部 ≥96 | 8/15 |

在这些任务上，**五个方法之间没有可测的差异**——判别力全部来自剩下 7~9 个任务（BoxNet、BoxLift、Path Plan、Letters(sentence)、Blocksworld、Game 24、MATH-Geometry）。

### 13.3 因素三：AveNorm 这把尺子会把分数抬高 4~15 点

AveNorm 的分母是"该任务内 5 个方法的最高分"。只要有一个方法接近满分，其它方法的比值就会被拉到接近 1。实测：

| 组 / 方法 | 平均准确率（15 任务） | AveNorm | 抬高 |
|---|---|---|---|
| off / OnlyQ | 81.4 | 90.3 | **+8.9** |
| off / All Text | 79.9 | 88.8 | +8.9 |
| off / All Code+CoT | 73.3 | 77.2 | +3.9 |
| off / AutoGen | 79.7 | 87.1 | +7.4 |
| off / Code+Text+Sum. | 84.6 | **99.4** | **+14.8** |
| on / Code+Text+Sum. | 83.8 | 99.7 | +15.9 |

**所以 99.4 不能读成"99.4 分"**，它真实的平均准确率是 84.6。Sum. 抬得最多，是因为在 BoxNet（16% vs 别人 0~8%）这类全组都低的任务上，它的比值被算成 1.0。

### 13.4 因素四：判分规则偏松（值约 2 分，主要"救"了代码类方法）

原仓库规则是"两个抽取答案里只要一个判对就算对"。改成"两个都要对"重算（`repro/strict_recount.py`，离线零成本）：

| 组 | OnlyQ | All Text | All Code+CoT | AutoGen | Code+Text+Sum. |
|---|---|---|---|---|---|
| A off 松 → 严 | 90.3 → 90.3 | 88.8 → 88.4 | **77.2 → 70.0（−7.2）** | 87.1 → 83.5 | 99.4 → 99.4 |
| B strip 松 → 严 | 94.8 → 94.4 | 89.7 → 89.7 | **89.1 → 77.4（−11.7）** | 92.7 → 92.0 | 99.4 → 99.4 |
| C on 松 → 严 | 94.3 → 93.5 | 91.4 → 91.2 | **90.5 → 89.3（−1.2）** | 93.2 → 93.6 | 99.7 → 99.7 |

结论：宽松规则对总分只贡献约 2 分，但**对代码类方法贡献 1~12 分**——因为代码方法经常"代码输出里没答案、正文里蒙对一个"，靠这条兜底判对。代码类方法的真实成绩比表面上更低。

### 13.5 不是原因的两项（查过了）

- **样本切片偏差**：担心"取前 25 个样本偏容易"。off 组前 25 个 AveNorm 90.3，后 25 个 94.9，全 50 个 89.8 → **前 25 个反而更难**，切片没有系统性乐观偏差。
- **判分器误判**：已交叉验证（12.3 节），MATH 上精确率 100%/99.6%，不是原因。

### 13.6 数据污染：做了改写实验，结论是"没证据支持记忆"（重要修正）

BBH / MATH / GSM-Hard / Game 24 / Letters 全是 2022–2023 年公开的数据集，2026 年的模型训练语料极可能包含原题。这一点没法直接证明，所以我们做了个**题面改写对照实验**（第 14 节），结论是：

> **Web of Lies 换成全新的场景、用词、人名、链长、追问位置后，准确率从 100% 变成 99.2%，没有下降。**

也就是说：这个任务的 100% 是"真会"，不是"见过"。**原先我根据 `Letters`（词级 100%）与 `Letters(sentence)`（句子级 68~88%）的落差推断"高分里有相当一部分是记忆"，这个推断站不住** —— 两者的任务形式不同（`Letters(sentence)` 还要求报出每个字母的位置、句子 8~25 词），难度本就高得多，分数低可以有更简单的解释。这一条以第 14 节的实验为准。

### 13.7 一句话总结

> 高分 = 2026 年模型确实强（代差）+ 一半题目已经太简单（饱和）+ AveNorm 归一化抬高 4~15 点 + 判分规则宽松（代码类多算 1~12 点）。
> **它证明的是"这篇论文的方法框架在今天的模型上依然成立（组合方法最优、代码不必更好），而不是"模型在这 15 个任务上得了 99 分"。**

想拿到更真实的水平，最有效的办法不是继续微调判分，而是换**更难的**任务/更长链条的题（第 14 节的实验说明：单纯换措辞不足以难倒它）。

目标：验证"饱和任务上的 100% 是不是因为见过原题"。

- **任务**：Web of Lies（原版三组都 100%、五个方法零差异，是最强的"疑似记忆"候选）
- **改写**：保留逻辑骨架（一条链式真话/谎话推理 + 一个已知事实 + 一个追问），换掉
  - 场景（村庄的诚实者/说谎者 → 档案室的办事员"reports accurately / fabricates"）
  - 全部人名（Vernell/Alexis… → Voss/Adair/Pell/Rune…，22 个自造姓氏）
  - 链长（原版 4~6 → 改写版 4~7）
  - 追问位置（原版固定问最后一人 → 改写版随机问中间或末尾的人）
- **真值**：用传播算法算（给定第一个人属性 + 每条陈述，逐条推出后面所有人），**不调 LLM 裁判**
- **对齐**：两个集合都用 25 题、都凑成 13 Yes / 12 No（原版直接取前 25 题是 10 Yes / 15 No，一个"永远答 No"的模型能白拿 60%，基线不一致就不能比）
- **成本**：2 集合 × 5 方法 × 25 题 = 250 次调用，脚本 `repro/run_wol_rewrite.py`

### 14.2 结果

| 方法 | 原版 | 改写版 | 差 |
|---|---|---|---|
| Only Question | 100.0% | 100.0% | ±0 |
| All Text | 100.0% | 100.0% | ±0 |
| All Code + CoT | 100.0% | 96.0% | −4.0 |
| AutoGen Concat. | 100.0% | 100.0% | ±0 |
| Code+Text+Sum. | 100.0% | 100.0% | ±0 |
| **平均** | **100.0%** | **99.2%** | **−0.8** |

唯一失分是 `All Code+CoT` 的 1 题（改写版第 16 题，正确答案 Yes，模型给了 No），属真实答错，不是格式问题。

抽查回答内容（`rewrite/1_only_ques_off/sample_1`）：模型逐条列出事实、按链逐人推属性（"Tobias says Durand reports accurately → since Durand does, Tobias's statement is true → Tobias reports accurately"），**是在推理，不是在套答案模板**。

### 14.3 结论

1. **改写没有难倒它** → Web of Lies 的 100% 是真实能力，不是数据集记忆。
2. 但这只否证了"这一题的饱和来自记忆"，**不能推广成"所有饱和任务都没有污染"** —— 改写仍保留了同一个推理模板，模型可能仍靠模板迁移。要更强的证据得换成需要真正新技能的长链题。
3. 对"为什么分数高"这个问题，改写实验把解释收窄了：**主因还是模型代差 + 任务本身太简单 + AveNorm 抬高 + 判分宽松**，而不是背题。

## 15. 数字乘法：题面形式与难度的对照

### 15.1 为什么挑这一题

Number Multiplying 在三组里都是 96~100%（5 个方法近乎零差异），是第二个"饱和到没有信息"的任务。论文里 GPT-4o 这一题只有 37%，差得最多，所以它最能检验一件事：**本次的 100% 是模型真会算，还是判分放水 / 题面格式带来的红利**。

### 15.2 实验 A：同一批数字，换题面

- **题目**：从数据集 `dataset_gather/number_multiply/` 取 25 题（`digit_1_2_4` 9 题、`digit_1_3_4` 8 题、`digit_1_2_2_4` 8 题），数字与标准答案都**直接读自数据集**（`input_value_list.txt` / `target_answer.txt`），不是我现编的
- **两个变体，数字完全相同**：
  - `orig`：原版裸表达式 —— `What is the result of -4*17*7571?`
  - `rewrite`：清单式商务场景 —— "A trading desk must reconcile several signed position adjustments… adjustment_1 = -4 … The net exposure is the product of all the adjustments."，**不出现 `*` 表达式**
- **判分**：取最后一个 `<<<...>>>`，抠出全部整数（去千分位逗号），与标准答案**精确整数比对**，不调 LLM 裁判 → 判分环节不引入任何宽松
- **结果**（`THINK_MODE=off`，250 次调用）：

| 方法 | 裸表达式 | 清单改写 | 差 |
|---|---|---|---|
| Only Question | 100.0% | 100.0% | ±0 |
| All Text | 100.0% | 100.0% | ±0 |
| All Code + CoT | 100.0% | 100.0% | ±0 |
| AutoGen Concat. | 100.0% | 100.0% | ±0 |
| Code+Text+Sum. | 100.0% | 100.0% | ±0 |

两个变体都顶到天花板，看不出题面有没有影响 —— 于是加做难度版。

### 15.3 实验 B：把算术本身加难

- **25 道新题**（`repro/data/nm_rewrite_hard.json`，固定种子 `Random(20261119)`）：4 个因子、位数 4/4/5/6、随机正负号，**乘积 18 位**（原版是 7~9 位）
- 两个变体、三种方法（只跑 OnlyQ / AllText / AllCode+CoT，150 次调用）
- **结果：三个方法、两个变体全部 25/25 = 100%，错 0 题**
- **人工抽查确认不是判分放水**（`repro/peek_nm_hard.py`，逐条打印回答 + 独立重算）：
  - OnlyQ，`-8880 × 1338 × 84147 × (-479558)`：回答 2,124 字，**手写长乘**、分块进位，中间结果 `478,898,227,674,720,000 + 557,881,442,677,440 = 479,456,109,117,397,440`，与标准答案逐位一致；**样本目录里没有任何 `.py` 文件** → 纯文本心算
  - OnlyQ，`-5502 × 3986 × 13598 × 631881`：用 `-5502 × (4000 − 14)` 拆项，同样逐位正确
  - All_code_CoT：写成 `result = -8880 * 1338 * 84147 * -479558; print(result)`，答案来自 stdout 的 18 位数，同样全对
  - 改写版的回答只是把 `adjustment_1 = …` 重新抄成算式，推理过程与原版完全同构

### 15.4 结论

1. **题面形式不影响成绩**：同一个数字，裸表达式和场景清单的准确率差 0。
2. **难度翻到 18 位乘积也不掉**：连"不给写代码"的纯文本方法都是 25/25，实测是逐步长乘算出来的，不是碰运气。
3. 所以 Number Multiplying 的高分**不是判分宽松、也不是格式红利，是模型真的会算**；反过来说，这个任务对 2026 年的模型已经饱和，**失去区分度**——论文里 GPT-4o 的 37% 是"当年不许用工具、纯心算不行"，不等于题目本身难。
4. 对论文"coding 不一定更好"这条结论的修正理解：至少在这一题上，代码方法没有优势的原因是**不用代码也能算对**，而不是"用了代码反而变差"。这和 §13 里 Blocksworld-All Code 12% 那种"用了代码反而变差"是两种不同的机制，不要混为一谈。
5. 两个改写实验（§14 Web of Lies、§15 数字乘法）合计 650 次调用、212K 输入 / 221K 输出 token，约 1.1~2.2 元。

## 16. 浮点超越函数计算：终于有区分度了

### 16.1 设计

§15 说明整数乘法连 18 位乘积都不掉分，于是加码到**不规则小数 + ln/根号/三角函数复合**——这种题手算不可能，只能写代码。

- **36 题、三档难度、各 12 题**（`repro/data/numeric_hard_tasks.json`，种子 `Random(20261120)`，可复现）：
  - L1 单个函数：`ln(181.8258)` = 5.203049086
  - L2 两三个函数组合：`exp(1.3532) + atan(3.3718)` = 5.152271458
  - L3 嵌套复合：`sin(ln(202.979) * 0.5768) * 1.6101` = 0.1238473867
- **反饱和设计**：所有取值都避开饱和区（`asin` 参数 0.1~0.7、`atan` 0.5~8、`sin/cos` 参数 0.2~1.2、`exp` 0.4~3.0），因为饱和区里答案对输入不敏感，会白送分
- **题面明确**：所有三角函数用弧度、要求至少 10 位有效数字、答案用 `<<<...>>>` 包住
- **真值**：Python `math` 双精度直接算；判分用**相对误差**，并同时给 1e-3 / 1e-6 / 1e-9 三档通过率
- **执行环境修正**：模型会写 `import mpmath` 求解高精度值，而 conda env 里 `pip` 不可用 → 手动下载纯 Python 的 `mpmath-1.4.1` wheel 解压到 `repro/vendor/`，并给子进程加 `PYTHONPATH`（这修掉了 AutoGen 前 3 题的假失败）

### 16.2 结果（相对误差 ≤ 1e-6 算对）

| 方法 | 总体 | L1 单函数 | L2 组合 | L3 嵌套 | 实际写代码 |
|---|---|---|---|---|---|
| Only Question | 80.6% | 91.7% | 75.0% | 75.0% | 0/36 |
| All Text | 75.0% | 75.0% | 75.0% | 75.0% | 0/36 |
| **All Code + CoT** | **100.0%** | 100% | 100% | 100% | 36/36 |
| **AutoGen Concat.** | **100.0%** | 100% | 100% | 100% | 36/36 |
| Code+Text+Sum. | 91.7% | 91.7% | 83.3% | 100% | 30/36 |

**这是整套复现里唯一一个"代码方法全面胜出"的任务**：写代码 = 100%，纯文本 = 75~80.6%，差 20~25 个点。

### 16.3 结论依赖精度要求（必须讲清楚）

同一批回答，只改"多接近才算对"：

| 方法 | 1e-3 | 1e-6 | 1e-9 | 中位相对误差 |
|---|---|---|---|---|
| Only Question | 100.0% | 80.6% | 19.4% | 1.75e-07 |
| All Text | 100.0% | 75.0% | 22.2% | 2.75e-07 |
| All Code + CoT | 100.0% | 100.0% | 100.0% | 6.11e-16 |
| AutoGen Concat. | 100.0% | 100.0% | 100.0% | 0.00e+00 |
| Code+Text+Sum. | 100.0% | 91.7% | 86.1% | 9.42e-16 |

- **放宽到 1e-3（论文 `is_equiv_func` 用的量级），五个方法全 100%，一点区分度都没有**
- 收紧到 1e-9，纯文本方法塌到 19~22%
- 分界线在"要求几位正确数字"：纯文本方法的中位相对误差是 1.8e-7~2.8e-7，也就是**大约 6 位可靠数字**，而题面要的是 10 位；代码方法是 1e-16 量级（双精度极限）

### 16.4 失败长什么样

- 纯文本方法的错误量级从 1e-6 到 6e-4 不等，典型：`sin(sin(0.63286)/sqrt(30.238))` 相对误差 5.9e-4、`atan(sin(0.79288)/sqrt(26.081))*1.3725` 4.8e-4、`log10(421.381)` 2.8e-5
- 也就是"算了个近似、前几位对、后面就不敢保证"——不是完全不会，是**精度不够**
- 难度的作用方向清晰：OnlyQ 在 L1 上 91.7%，到 L2/L3 掉到 75.0%（中间值需要自己算，误差累积）
- `1_only_ques` 全程 0/36 写代码（题面没让写），`All_text` 也是 0/36 —— 这就是差距的来源
- `Text_code_summarizer` 91.7%（30/36 写代码）：它拿到 All Code 那一路的答案后可以直接抄，所以明显好于纯文本；但它自己重算时会引入新的精度误差

### 16.5 对论文结论的意义

1. 论文说"coding 不一定更好"，本实验给出了它的**另一半**：任务要求高精度数值计算时，coding 是决定性的——**方法优劣取决于任务需要什么**，不是代码本身有魔力。
2. 这也解释了 §3 里为什么原数据集那些任务代码方法没优势：它们的答案要么是短 token（BBH）、要么算术简单到心算能做，代码带不来额外信息。
3. 若按论文的 AveNorm 口径把这题算进去，5 个方法的排序会被这一个任务明显拉开（100 / 100 / 91.7 / 80.6 / 75.0），说明**任务集里有没有这种"必须算准"的题，会直接决定论文的方法排名**。

### 16.6 成本

5 个方法 × 36 题 = 183 次调用，108.9K 输入 / 117.9K 输出 token，约 0.6~1.2 元。脚本 `repro/run_numeric_hard.py`（`--rejudge` 可离线重判，不花钱）。
